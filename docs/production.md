# 生产部署与验收记录

记录时间：2026-10-14（UTC+8）。在线入口：[shot.l2cl.link](https://shot.l2cl.link)。这是当时的验收快照，后续服务状态可能变化。

## 拓扑

```text
客户端
  → Cloudflare Worker（公开 GET 的边缘图片缓存 + 全局内容版本）
  → Nginx HTTPS
  → 127.0.0.1:3030 Node.js
  → 常驻本地 Chrome / 5 个预热 Page
  → SQLite Worker / 私有图片缓存

边缘命中 → 异步签名统计请求 → 源站 SQLite
```

源站使用 Ubuntu 24.04 x86_64，约 1GB RAM、2GB swap。运行时为 Node.js 24.21.0 LTS、本地 Google Chrome 155.0.8059.79；依赖锁定 Puppeteer Core 25.13.0、ipaddr.js 2.5.0。

部署路径是 `/opt/webshot/app`，服务为 `webshot.service`。5 个常驻 Page、最多 7 个 Page，单队列总等待上限 40 项；系统内存不足时排队。实际 systemd 内存限制为 High 700MiB、Max 800MiB、SwapMax 256MiB，生产通过持久属性覆盖实现；仓库模板直接包含同样数值。

HTTP/HTTPS 由 Nginx 提供，Chrome 保留沙箱；出站隔离限制在专用服务 UID 内。证书自动续期。Worker 仅路由 `shot.l2cl.link/*`。公共仓库中的配置是可编辑模板，不包含实际账号/zone ID、密钥或私人运行数据。

## 1GB VM 调整与复测（2026-10-14）

生产保持 5 个预热 Page、最多 7 个 Page；新增独立的渲染并发上限 3，CPU / 内存 / I/O
压力升高时降到 2，停止临时扩容。Page 预设默认 PC 参数并跳过重复设置；初始导航复用本次
刚完成的公网地址校验，其它源仍校验。Cookie / 存储清理和 about:blank 保留，显式 GC 串行执行。

Linux zswap 已启用，压缩池上限为 RAM 的 10%，原 2GB 磁盘 swap 和 swappiness=20 保留；
`webshot-zswap.service` 开机恢复配置。Chrome 选择原生共享内存，实际映射已确认出现
`memfd:shared-memory-region`。回滚步骤见运行文档。

有限样本如下，记录的是实际渲染时间，均用 `$force=1`；不同阶段主机压力不同，不能据此计算
可靠的优化百分比或 P95：

## 历史文档保留修复（2026-10-14）

在同一台 1GB VM 的 Chrome 155 中，使用 1 个常驻 Page 顺序对照两种策略。
固定页面每次创建 32MiB 页面内存，连续截图 3 次，均执行 about:blank、Cookie/存储清理和 GC。
旧策略在第 3 次清理后保留 7 个历史条目，并可通过后退恢复同一个随机状态，证明旧文档仍被 BFCache 保留。
旧策略渲染进程从 1 个增加到 4 个；浏览器各进程私有内存之和从 139.2MiB 增至 228.3MiB。

新策略关闭 BFCache，并在空闲时清除导航历史。每次清理后只有 1 个历史条目、1 个渲染进程；
浏览器私有内存为 146.6 / 145.2 / 145.7MiB（起始 135.4MiB）。末次比旧策略少约 82.6MiB。
六张 PNG 哈希完全一致；Page 对象、HTTP 静态资源缓存、同身份排队复用和持久 PNG 缓存保留。
这是一项单 Page、固定页面的内存对照，不能乘以 5 作为生产节省量，也不能推导所有网站的速度提升比例。

旧策略渲染 2615 / 2397.5 / 1686.2ms，新策略 874.6 / 351.2 / 289.2ms。
两组顺序执行，包含冷缓存和宿主机调度差异；内存保留与冻结文档恢复已有直接证据，耗时百分比不作因果承诺。

新版本前置拒绝非法目标，不读取图片缓存、不领取 Page、不触发浏览器清理。
拦截计时按请求采集校验等待与 CDP 放行等待，仅持久化数值；并行请求的累计等待有重叠。
27 项单元回归及真实 Chrome 的方法/Body/鉴权/尺寸/整页/同身份复用/身份切换清理均通过。
固定页面对照脚本为 `test/history-integration.mjs`，重复部署不依赖临时脚本。


部署后验收：5 个 Page 空闲且各仅保留 1 条历史；`history_cache_disabled=true`；浏览器仍只启动一次。
非法 `/owa` 返回 400，前后渲染峰值和所有 Page 队列均未变化。
真实 Google 冷请求两次导航超时：一次处理器只等待 8.9ms，服务 I/O 阻塞约 81.5%、重大缺页 873 次，
说明这次 15 秒等待不能归因于 Node 放行逻辑；另一次 CDP 放行约 1.09s，亦不足以解释全部超时。
随后 Google 渲染成功 5.447s：34 次暂停、新源校验 3 次，校验累计 174ms、最长 87ms，
CDP 累计 722ms、最长 300ms。这些累计值有并行重叠，不能直接加总为关键路径。
example.com 渲染 778ms，处理器累计约 10ms。冷 I/O 和宿主机 CPU 争用仍未完全消除，
没有把固定页面的内存修复表述为所有网站延迟已经解决。父级资源限额检查另行记录。
本次源码回滚包：`/opt/webshot/backups/history-20261014T092729Z/app.tar`。

## 冷导航进程定位与预读调整（2026-10-14）

新增 `navigation_progress` 在导航失败时也保留主文档进度。独立真实 Chrome 夹具验证了
“主文档完成但阻塞脚本未就绪”的超时，并验证四种方法、二进制 Body、鉴权隔离、尺寸和常驻 Page。
30 项单元回归通过，包括重定向、子框架过滤、隐私字段和响应事件晚于传输完成的计时。

调整前同一个 Example 页面冷渲染 5.841s，紧接着为 0.295s；冷窗口 CPU 约 0.243s，
拦截处理累计约 8ms，服务 I/O 阻塞 65.8%。进程探针观察到 Chrome 渲染进程 D 状态，
等待 `folio_wait_bit_common` 并发生实际读取；一批约 1.8MiB 读取累计耗时约 210ms。
另一次 Google 渲染 3.960s、CPU 0.593s，主文档 TTFB 34.6ms；整个请求中的浏览器、渲染器、
Node 均出现读盘缺页等待，不能将这个延迟解释成目标站 TTFB 慢。

云 API 只读确认该实例启动盘 47GB、10 VPU/GB、自动调优关闭；没有修改云资源或计费档位。
根盘预读原为 2048KiB。使用同一份 32MiB 临时文件，每次随机访问 32 个固定的稀疏页，
每轮仅对测试文件执行 `POSIX_FADV_DONTNEED`，不清理生产文件或全机缓存；按 A/B/B/A 交叉执行：

| 预读 | 实际物理读取 | 缺页访问耗时 | 重大缺页 |
| --- | --- | --- | --- |
| 2048KiB | 32MiB | 2875.8ms | 22 |
| 128KiB | 4MiB | 234.7ms | 32 |
| 128KiB | 4MiB | 72.1ms | 32 |
| 2048KiB | 32MiB | 2893.3ms | 21 |

四轮校验和相同，结束恢复原预读并删除测试文件。该实验直接证明在本机稀疏缺页访问中，
大预读放大了读取量；这是独立文件访问实验，不是所有网页截图速度的因果百分比。
随后通过 `webshot-readahead.service` 持久应用 128KiB，保留原值以供停止时恢复，并重启 Chrome
以重新打开映射。仍保留 5 个预热 Page、沙箱及原网络和存储配置。

| 应用后请求 | Example 渲染 | Google 渲染 |
| --- | --- | --- |
| 重启后的首轮，透传探针 UA | 0.798s | 0.977s |
| 紧接着重试，透传探针 UA | 0.262s | 0.496s |
| 空闲后，显式 `$device=pc` | 4.280s | 3.264s |

全部 `$force` 绕过截图缓存；均 HTTP 200。UA 和目标内容不同的行不作同负载速度比较。
Example 仍有长尾：主文档请求事件在 1377ms 才送达，响应事件 2748ms、DOM 3635ms，
重大缺页 1169 次、服务 I/O 阻塞 78.7%。Google PC 页暂停资源 37 次，CPU 4.038s、
Steal 58.7%，主文档响应头等待约 91ms、导航 1.579s，此次主要受 CPU 争用影响。
没有将预读修复表述为完全消除了冷请求。进程读取计数可能继承到 fork 子进程，不能
直接将所有 PID 累计读数相加作为磁盘实际读取总量；需以 block device 计数核验。

预读回滚及源码回滚分别执行，见 `docs/operations.md`。
最终源码备份 `/opt/webshot/backups/readahead-20261014T101207Z/app.tar`。

## 长尾研究与空闲身份切换修复（2026-10-14）

本轮官方文档、类似 issue、实验优先级和只读文件驻留观察见 `docs/cold-navigation-research.md`。
性能部分未改变 swappiness、GC 策略、浏览器类型或 5 个预热槽位；6.575s→0.402s 的两个
Example 样本是自然空闲/文件驻留观察，不能当作新性能调参的效果。

核验缓存清理时发现：原代码只在排队任务切换身份时重建 context，空闲槽位切换身份遗漏。
合成自定义鉴权 Header 的夹具，目标返回 private,max-age=3600，A→A→B 最后仍显示 A；
补充 A→匿名夹具也复现旧身份内容。
已修复为在任务领取后、渲染前核对 context 实际身份；同身份可继续使用 HTTP 缓存，
所有身份变化都会获得新 context。公开与私有 PNG 均使用 scope v2，绕过全部旧策略图片；
源站与 Cloudflare Worker 必须同步更新，30 天缓存机制继续使用，新版本重新填充缓存。

32 项单元回归、本机真实 Chrome 和源站 Chrome155 的缓存隔离夹具及完整 API 夹具通过。
缓存夹具验证同身份只请求一次主文档，换身份请求新的主文档并返回 B 或匿名内容；空闲及排队身份
切换、二进制 Body、四种方法、设备、尺寸和导航超时进度均已覆盖。合成身份只发送到独立
测试回环服务，未使用真实凭据；没有据此认定曾经泄露真实数据。
部署前源码备份 `/opt/webshot/backups/idle-identity-20261014T110640Z/app.tar`。

全部缓存键同步发布后，公网 Example 验证为 REFRESH 1.762s → EDGE-HIT 0.233s / 0.230s，
三次完整 PNG 均为 87715 字节且哈希一致。这是热态链路验收，不能当作冷导航优化效果。
Worker 版本 `1bbdd2c1-61e9-47ce-8c4c-7dac5087268d`，现有 Secret 与 Durable Object
命名空间绑定保持一致。源站启动次数 1、5 个槽位全部就绪、无排队、NRestarts=0；
swappiness=20、预读=128KiB，未更改 GC 策略或浏览器类型。
