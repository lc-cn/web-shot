# 生产部署与验收记录

记录时间：2026-10-14（UTC+8）。在线入口：[shot.l2cl.link](https://shot.l2cl.link)。这是当时的验收快照，后续服务状态可能变化。

## 拓扑

```text
客户端
  → Cloudflare Worker（公开 GET 的边缘图片缓存 + 全局内容版本）
  → Nginx HTTPS
  → 127.0.0.1:3030 Node.js
  → 常驻本地 Chrome / 5 个预热 Page
  → SQLite Worker / 私有图片缓存

边缘命中 → 异步签名统计请求 → 源站 SQLite
```

源站使用 Ubuntu 24.04 x86_64，约 1GB RAM、2GB swap。运行时为 Node.js 24.21.0 LTS、本地 Google Chrome 155.0.8059.79；依赖锁定 Puppeteer Core 25.13.0、ipaddr.js 2.5.0。

部署路径是 `/opt/webshot/app`，服务为 `webshot.service`。5 个常驻 Page、最多 7 个 Page，单队列总等待上限 40 项；系统内存不足时排队。实际 systemd 内存限制为 High 700MiB、Max 800MiB、SwapMax 256MiB，生产通过持久属性覆盖实现；仓库模板直接包含同样数值。

HTTP/HTTPS 由 Nginx 提供，Chrome 保留沙箱；出站隔离限制在专用服务 UID 内。证书自动续期。Worker 仅路由 `shot.l2cl.link/*`。公共仓库中的配置是可编辑模板，不包含实际账号/zone ID、密钥或私人运行数据。

## 性能样本

以下目标均为 `example.com`，图片约 87.7KB。样本数量较少，不能代表所有网站、网络或并发负载；同一连接与新连接的差异也包含 TLS/连接建立时间。

| 场景 | 完整图片返回耗时 |
| --- | ---: |
| 同一连接，边缘命中 | 0.315s、0.311s |
| 默认 GET，复用连接，边缘命中 | 0.384s |
| 新连接，边缘命中样本 | 1.346s |
| 强制刷新 | 5.675s |

强制刷新样本实际渲染 4.233s：公网地址校验 204ms、Page 设置 591ms、导航 1356ms、资源等待 1611ms、截图编码 472ms。排队约 0.2ms。简单页面的其它样本曾出现 0.66–17.45s 的渲染波动，不能把预热或单次快样本当作固定延迟承诺。

- 本机独立真实 Chrome：GET/POST/DELETE/PATCH、二进制 Body、鉴权 Header、UA、指定宽度与整页高度、about:blank 清理、同上下文复用与鉴权切换隔离。

## 1GB VM 调整与复测（2026-10-14）

生产保持 5 个预热 Page、最多 7 个 Page；新增独立的渲染并发上限 3，CPU / 内存 / I/O
压力升高时降到 2，停止临时扩容。Page 预设默认 PC 参数并跳过重复设置；初始导航复用本次
刚完成的公网地址校验，其它源仍校验。Cookie / 存储清理和 about:blank 保留，显式 GC 串行执行。

Linux zswap 已启用，压缩池上限为 RAM 的 10%，原 2GB 磁盘 swap 和 swappiness=20 保留；
`webshot-zswap.service` 开机恢复配置。Chrome 选择原生共享内存，实际映射已确认出现
`memfd:shared-memory-region`。回滚步骤见运行文档。

有限样本如下，记录的是实际渲染时间，均用 `$force=1`；不同阶段主机压力不同，不能据此计算
可靠的优化百分比或 P95：

| 阶段 | example.com | showlogin.cc |
| --- | --- | --- |
| 原配置、持续运行 | 3.908 / 0.408 / 0.314s | 6.388 / 12.595 / 3.211s |
| 单独启用 zswap | 1.382 / 0.241 / 0.325s | 6.717 / 3.332 / 4.482s |
| 调度及共享内存调整后 | 5.052 / 0.744 / 0.272s | 一次 504、11.728 / 4.795s |
| 最终版本、重启后 | 11.169 / 1.305 / 1.105 / 0.997s | 未继续对该目标重复施压 |

调整后的首个 example.com 样本同时有一次公网刷新；各组首个请求可能包含冷启动影响。
showlogin.cc 部分图片约 5.8KB，正常页面约 133KB，说明目标内容并不固定，不能把不同内容的
渲染当作相同负载。最终复测出现较高宿主机 CPU Steal，热请求没有证明整体耗时优于原配置。
改动已验证资源调度和请求正确性，外部延迟与长尾仍存在。

最终六个不同宽度的并发刷新全部 HTTP 200，观察到实际并发峰值 2，完整响应约 1.10–5.19s，
含排队。结束后浏览器只启动过一次，5 个 Page 全部空闲且为 about:blank，无待处理任务、
无 OOM 或内存限流事件。四种方法、Body、鉴权、整页高度及上下文切换已通过最终真实 Chrome
测试；初始源每次渲染只进行一次地址校验。公网刷新返回 200，边缘命中图片与刷新图片字节一致。
